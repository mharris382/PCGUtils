You are working inside my Unreal Engine 5.8 C++ plugin repository named PCGUtils.

The repository either already contains, or is currently implementing, a module named:

PCGUtilsMaterialCache

That module contains a world-scoped material variant cache that resolves:

Parent material + parameter configuration
-> shared immutable UMaterialInterface

Extend this module with a complementary actor-local material cache system.

The local system should allow PCG and Blueprint code to automatically create, retain, retrieve, and reuse mutable UMaterialInstanceDynamic objects associated with specific actor components.

The primary use case is gameplay-driven procedural content.

Example:

* A spline component authors a gunpowder trail through PCG.
* PCG creates one mutable MID for that spline component.
* Every generated point belonging to that spline receives the same local MID.
* The spline component does not need to create the MID or manually pass it into PCG.
* Gameplay later retrieves the MID associated with that spline component.
* Gameplay modifies parameters such as BurnProgress, IgnitionPosition, or FireIntensity.
* Other spline components have independent local MIDs and are unaffected.

The system should support UActorComponent instances as logical material owners.

The public API and PCG node should provide convenience paths that accept either:

* A direct UActorComponent reference
* A component soft object path
* A component-derived name/key

Callers should not be required to manually convert:

Component -> Soft Object Path -> Name

before resolving or retrieving a material.

Likewise, a PCG graph should be able to provide a soft-object-path metadata attribute referencing a component, and the material node should resolve that component and derive the appropriate local owner key internally.

CORE ARCHITECTURE

The module should contain two complementary material authorities.

GLOBAL MATERIAL VARIANT CACHE

World-scoped.

Canonical material request
-> shared immutable UMaterialInterface

Properties:

* Content-addressed
* Shared across callers in one world
* Must not be mutated after resolution
* Returned as UMaterialInterface*

LOCAL MATERIAL CACHE COMPONENT

Actor-scoped.

Owner component identity + binding name + optional variant name
-> locally owned mutable UMaterialInstanceDynamic

Properties:

* Owned by an actor-local cache component
* Mutable for gameplay
* Reused across PCG regeneration when appropriate
* Returned as UMaterialInstanceDynamic*
* Lifetime follows the actor and cache component

Do not store mutable local MIDs inside the global content-addressed cache.

Once gameplay mutates a local MID, its current values no longer correspond to the canonical initialization request. The canonical request should only represent how the local MID was initially created.

2. LOCAL MATERIAL BINDING KEY

A local material should be addressed by:

Owner component + binding name + optional variant name

Conceptually:

struct FPCGUtilsLocalMaterialBindingKey
{
FName OwnerComponentKey;
FName BindingName;
FName VariantName;
};

The exact internal structure may differ.

Requirements:

* The key must be deterministic within the owning actor.
* Different sibling components must not collide.
* Different bindings on one component must not collide.
* Different variants under one binding must not collide.
* NAME_None should be valid for the optional variant.
* The key should be usable efficiently in a TMap.
* Hash equality and structural equality must agree.

Because the cache component is actor-local, the owning component’s FName may be sufficient as the internal owner key when the component belongs to the same actor.

However, inspect the actual ownership scenarios and Unreal object-path behavior before finalizing this.

If external components belonging to another actor are supported, the key must include enough path or actor identity information to remain unambiguous.

Do not assume that GetFName() alone is globally unique.

6. LOCAL MATERIAL RESOLUTION

Implement a local resolution API similar to:

UMaterialInstanceDynamic* ResolveLocalMaterial(
UActorComponent* OwnerComponent,
FName BindingName,
FName VariantName,
const FPCGUtilsMaterialVariantRequest& InitialConfiguration);

The VariantName argument may default to NAME_None.

Resolution behavior:

1. Validate the owner component.
2. Validate that it belongs to the local cache component’s actor, unless external ownership is intentionally supported.
3. Derive the owner-component key.
4. Build the local binding key.
5. Validate and canonicalize the initialization material request.
6. Search for an existing local entry.
7. If no entry exists:

   * Create a unique MID.
   * Apply the initialization parameters.
   * Store the MID and initialization key.
   * Return the MID.
8. If an entry exists and its initialization key matches:

   * Return the existing MID.
   * Do not reapply initialization values.
   * Preserve gameplay-modified parameter values.
9. If an entry exists but the initialization key changed:

   * Create a replacement MID.
   * Apply the new initialization configuration.
   * Replace the entry.
   * Return the replacement MID.
10. Never add the local MID to the global shared cache.

The component should reuse the existing canonical material request logic and parameter-application logic from the global cache.

Do not mutate an existing MID to force it to match a changed authoring configuration. Create a replacement so stale gameplay state does not mix unpredictably with a new base configuration.

16. PCG BINDING CONFLICT VALIDATION

Detect this conflict:

Same cache component
Same owner component
Same binding name
Same variant name
Different initialization requests

Example:

Variant = Default
Texture = T_Gunpowder_A

and:

SplineComponent_A
Binding = GunpowderTrail
Variant = Default
Texture = T_Gunpowder_B

These requests attempt to assign two incompatible initialization configurations to the same mutable local binding.

Do not use nondeterministic last-request-wins behavior.

Report an error similar to:

Failed conflicting entries should receive null unless established PCGUtils conventions specify another safe behavior.

17. PCG SOFT-PATH RESOLUTION AND THREADING

Resolving soft object paths and creating MIDs involves UObject access.

PCG may execute work off the game thread.

Separate processing into safe phases.

WORKER-COMPATIBLE PHASE

* Read plain metadata where permitted.
* Collect owner representations.
* Collect soft paths.
* Build plain material-request values.
* Group raw requests where possible.

GAME-THREAD PHASE

* Resolve component soft object paths.
* Validate component ownership.
* Find local cache components.
* Canonicalize any UObject-dependent asset values.
* Resolve or create local MIDs.
* Write UObject references into output metadata when required.

Use the established UE 5.8 PCG game-thread handoff or context pause/resume pattern already used in the repository or engine source.

Do not call ResolveObject, TryLoad, create MIDs, or mutate UObjects from an unsafe worker thread.

Load each unique component or asset path at most once per execution where practical.
